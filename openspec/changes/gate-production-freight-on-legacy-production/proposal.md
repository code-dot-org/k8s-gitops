## Why

The `cdo-rails` image promoted into the `production` namespace must never be built from a commit newer than the one legacy production runs: the image carries no migrations, schema changes reach the production database only through the legacy EC2 deploy, and a worker running code ahead of that schema fails jobs confusingly. Today nothing enforces the rule. The only control is a human at the Kargo gate (`autoPromotionEnabled: false`), and that human cannot even tell which commit a Freight came from, because the image index carries no commit and the Warehouse follows the mutable `latest` tag by digest. This change makes the rule machine-enforced, and is required before we turn the production deployment on. The k8s staging and test namespaces share their databases with legacy staging and test and already run staging-built images ahead of them, so the runtime half of the change applies there too.

Precisely: a k8s image is built from a `staging` commit, while legacy production runs a merge commit on the `production` branch, so "the same commit is running in legacy production" means the image's source commit is contained in (is an ancestor of, or equal to) the commit legacy production runs. Running behind is safe with respect to the hazard this change addresses: an older image has no unapplied migration prerequisites. It is not a guarantee that older code works against a newer schema. The repository ships destructive migrations every year (tables and columns dropped or renamed), and an image from before such a migration can pass both gates and still break, exactly as a legacy code rollback would. The gates certify the first property only; the runbook's rollback procedure carries the second.

## What Changes

- **Image provenance (code-dot-org CI).** Every published `cdo-rails` index becomes an OCI image index annotated with `org.opencontainers.image.revision` = the staging commit it was built from, so Kargo Freight carries the commit. The image also ships `dashboard/db/migrate_versions.txt`, the list of migration versions the code expects, generated at build time. `db/migrate` itself stays out of the image.
- **Kargo commit gate (k8s-gitops).** The `production` Stage promotion template gets two `http` steps before anything is cloned or written, both asking GitHub to compare the Freight's commit with the `production` branch: `freight-has-revision` fails when the revision is missing or unknown, and `revision-in-legacy-production` fails when the commit is ahead of or diverged from the branch. Kargo 1.9.5 cannot attach custom text to an `http` failure, so the failing step's name is the diagnostic. **BREAKING** for the Kargo path: Freight built before the CI change has no annotation and can no longer be promoted to production. Intentional; no Freight is in production today.
- **Runtime schema guard (code-dot-org chart + k8s-gitops values).** Chart Deployments gain an opt-in `schema-guard` initContainer that compares the image's migration set with `schema_migrations` in the target database and refuses to start the pod when any expected migration is missing. Production enables it in `enforce` from its first pod: at first enablement there is no k8s capacity to protect and legacy carries every job, so a false block costs nothing, while `warn` would start a worker in the very state the guard exists to prevent. Staging enables it in `warn` for one rollout, to read the comparison against a real legacy database and surface any false positive before production, then moves to `enforce`. Test stays in `warn` until its gap has been measured. Deployments switch to RollingUpdate with `maxUnavailable: 0` so a blocked pod never reduces running capacity.
- **Promotion runbook (k8s-gitops).** New `docs/production-promotion.md`: the rule, the two gates, what the human still verifies, rollback, timing, failure signatures and the hotfix caveat. Linked from the Kargo project directory.
- **Unchanged on purpose.** Promotion to production stays a manual decision; who may promote is not narrowed; the Kargo commit gate applies to `production` only, since for staging it is trivially true and for test it would fail every auto-promotion until the next DTT; no new cluster infrastructure (no policy engine, no Argo Rollouts, no tofu).

## Capabilities

### New Capabilities

- `cdo-rails-image-provenance`: the published image index names its source commit and the image carries the migration version set it expects.
- `production-freight-commit-gate`: Kargo refuses to promote Freight to `production` unless its commit is contained in the legacy `production` branch; fails closed.
- `production-schema-guard`: pods in every envType that shares a legacy database (production, staging, test) verify, before the application starts, that every migration the image expects is applied in that database; fails closed without reducing running capacity.
- `production-promotion-runbook`: the manual procedure around the gates: pre- and post-promotion checks, rollback, failure signatures, and the policy that production promotion stays manual.

### Modified Capabilities

None. `openspec/specs/` holds no existing capabilities.

No chart under `apps/` changes, so no `Chart.yaml` bump there; no `apps/app-of-apps` structure change, so no mimic-tree edit.
- **Runtime behaviour**: two GitHub API calls per production promotion from the Kargo controller (unauthenticated, 60/hour limit); one short MySQL query per pod start in staging, test and production; staging rollouts may stall for up to one legacy build cycle when a migration races the image; test logs its gap in `warn` mode; new failure states operators must recognise (Promotion failed at `freight-has-revision` or `revision-in-legacy-production`; pod `Init:Error` with `schema-guard` logs; Argo `Degraded` while a rollout waits for the legacy deploy).
- **Sequencing**: the chart change must reach the `production` branch through a normal DTP before the production deployment is enabled (a separate change), and that enabling change must also switch the production deployment from its current `branch: staging` (a FIXME left for faster testing) to `branch: production`, so chart and image come from the same lineage; the Kargo steps can land any time after the first annotated image exists. Any NetworkPolicy added later must keep allowing the init container's DB egress and the Kargo controller's GitHub egress.
