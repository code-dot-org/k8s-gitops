## Why

The change `gate-production-freight-on-legacy-production` makes the manual promotion of Freight into the `production` namespace safe: a Kargo step rejects Freight whose commit is not yet in the legacy `production` branch, and a schema guard refuses to start a pod whose migrations are not in the database. It does not press the button. After every legacy production deploy (DTP) a person still has to notice that it finished, find the Freight built from the matching `staging` commit, and promote it. That is toil, it leaves k8s production behind legacy for as long as nobody is looking, and it is exactly the kind of step that gets skipped. This change automates the button: when legacy production publishes a release, the image built from the staging commit that release contains is promoted to `production`, with both gates still in force.

### The whole plan, for reviewers

This is step two of a two-step plan. Read both changes together.

1. **Gate it** (`gate-production-freight-on-legacy-production`, prerequisite). Every published `cdo-rails` image index carries the staging commit it was built from (`org.opencontainers.image.revision`). The production Stage's first two promotion steps ask GitHub whether that commit is known and contained in the `production` branch and fail the promotion otherwise. Every Deployment pod in production, staging and test runs a `schema-guard` initContainer that compares the image's migration set with `schema_migrations` and blocks without reducing running capacity. Promotion stays manual and a runbook covers the procedure.
2. **Automate it** (this change). The legacy production release becomes the trigger. A code-dot-org workflow resolves the staging commit the release contains, moves the `cdo-rails:production` tag to that commit's existing image, and a second Kargo Warehouse that follows that tag feeds the production Stage with auto-promotion on. The gate from step one runs on every automatic promotion. The schema guard is unchanged.

Step two depends on step one being rolled out: production running with the guard in `enforce`, and a few manual promotions done from the runbook so a person has watched the gates and the first production workloads before a robot takes over. It also depends on a small legacy change: today the release tags the `production` branch tip at the moment it is created, not the revision the deploy ran, so the release must first be made to name the deployed revision.

## What Changes

- **Legacy release identity (code-dot-org, prerequisite).** `bin/create-release` gains `--commit <sha>` and `publish_github_release` passes the revision the build deployed, so the release tag names what legacy production is actually running instead of the branch tip at release time. This also makes the tag consistent with the release's own changelog, which is already computed from the deployed checkout.
- **Production image tag (code-dot-org).** A new workflow runs when a GitHub release is published and acts only on eligible releases: not a draft or prerelease, a production-format tag, a merge commit contained in `production`. It asks the GitHub compare API for the merge base of `staging` and the release commit, which is the staging commit the release contains, requires that CI published an image for exactly that commit, and resolves that image to a digest once. It validates the index by digest, writes the `cdo-rails:release-<tag>` alias, confirms the release is still the newest, and only then moves the mutable `cdo-rails:production` tag, all by digest with regctl, which preserves the digest and the revision annotation. Runs are serialized, a non-latest release can only write its alias, an existing alias is never repointed without an explicit input, failures are classified as published or not, and every failure notifies a person. A missing exact image fails the run with candidate ancestors for an operator to choose after a compatibility review; nothing older is promoted automatically. A `workflow_dispatch` entry point re-runs it for a named release, with an optional commit override that must be contained in that release.
- **Production Warehouse and auto-promotion (k8s-gitops).** A second Warehouse follows `cdo-rails:production` by digest, exactly as the existing one follows `latest`. The `production` Stage requests Freight directly from that Warehouse instead of from `test`, and the project promotion policy turns `autoPromotionEnabled` on for `production`. **BREAKING** for the manual flow: Freight from the shared Warehouse, including Freight verified in `test`, can no longer be promoted to production; only Freight from the production Warehouse can. Rollback becomes a manual promotion of an older production-Warehouse Freight, which Kargo does not undo until a release yields a new digest; every rollback, including to the previous release, follows the runbook's destructive-migration review, since the gates certify missing prerequisites only. The Warehouse is seeded with the previous and current releases before the Stage switches to it, so a rollback target exists from the first automatic promotion.
- **The gate stays, the runbook changes.** The two gate steps, `freight-has-revision` and `revision-in-legacy-production`, keep running first on every promotion, now including the automatic ones, as defense in depth against a mis-resolved commit. The runbook describes what the automation does, how to confirm which release a digest came from and whether that digest ran in `test`, how to pause the automation with one commit, how rollback behaves, and what to do when the workflow fails before or after publishing, or the gate fails. Its requirement that promotion remains a manual decision is removed.
- **Unchanged on purpose.** The schema guard and its modes; the `staging`, `test` and `levelbuilder` Stages; who may create a Promotion; no new cluster infrastructure. The alternative that keeps a single Warehouse, an in-cluster job that creates Promotions, is recorded in the design and not chosen.

## Capabilities

### New Capabilities

- `cdo-rails-production-tag`: the legacy release names the deployed revision; on every eligible release the `cdo-rails:production` tag is moved, by digest and live tag last, to the exact image of the staging commit the release contains, aliased per release, serialized against other runs, and every failure notifies a person.
- `production-freight-auto-promotion`: a dedicated Warehouse, seeded with the previous and current releases before cutover, turns each move of that tag into Freight; the production Stage promotes it without a person; manual rollback is reviewed and sticks; failed promotions are recovered by hand; and the automation can be paused with one commit.

### Modified Capabilities

Both come from `gate-production-freight-on-legacy-production`, which must be archived into `openspec/specs/` before this change is applied.

- `production-freight-commit-gate`: the requirement that the gate applies to every promotion drops its clause that `autoPromotionEnabled` stays `false` for `production` and gains the automatic promotion as a scenario.
- `production-promotion-runbook`: the runbook describes the automated procedure and the person's role around it; the requirement that promotion remains a manual decision is removed.

## Impact

- **code-dot-org** (two PRs to `staging`): first `bin/create-release` and `lib/rake/infra.rake` (release identity, reviewed by the legacy deploy owners); then new `.github/workflows/cdo-rails-production-tag.yml`, new `docker/rails/tag-production-image.sh`, `docker/rails/README.md` tag contract. No image content or chart change. The workflow runs on the release's tag commit, so it only starts firing after a DTP has carried it to the `production` branch.
- **k8s-gitops**: new `apps/kargo/projects/codeai/warehouse-production.yaml` (picked up by the project Application's recursive directory source), `apps/kargo/projects/codeai/stages/production.yaml`, `apps/kargo/projects/codeai/project-config.yaml`, `apps/kargo/projects/codeai/README.md`, `docs/production-promotion.md`. No chart under `apps/` changes, so no `Chart.yaml` bump; no `apps/app-of-apps` structure change, so no mimic-tree edit.
- **Runtime behaviour**: one short GitHub Actions run per legacy release (a few GitHub API calls and one in-registry copy); one more tag for Kargo to watch; production rollouts start within minutes of a release instead of when a person acts. New failure states: the workflow fails before the live tag moves (nothing changed, k8s production stays on the previous release) or at or after it (state unknown until the operator inspects the registry and Kargo); the exact image is missing (run fails with candidates, operator decides); a Promotion fails at a gate step (Kargo never retries that Freight; a transient cause is recovered by promoting the same Freight by hand, a wrong digest by a corrected tag move that yields new Freight).
- **Sequencing**: step one rolled out first; the release identity change merged, carried to `production` by a DTP and observed on a release; the workflow merged and carried to `production`; a failure notification tested; the Warehouse added in its own k8s-gitops commit; the `production` tag seeded with the previous and then the current release so the Warehouse holds two Freight; then the Stage switch and auto-promotion in a second commit.
